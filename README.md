# OpenCode Telegram Bot — Railway Edition

A production-oriented Telegram client for [OpenCode](https://github.com/anomalyco/opencode) built to run continuously on Railway. It turns Telegram into a persistent OpenCode workspace: coding sessions, model routing, Telegram Topics, history, files, custom providers, GitHub/MCP integrations, memory, scheduled tasks, audio/image workflows, and operational controls.

> **Current architecture:** the bot is no longer just a simple Telegram wrapper. The runtime is organized around persistent sessions, canonical model routing, and explicit Telegram-context bindings so normal chats and forum Topics can safely coexist.

## Highlights

- 🤖 OpenCode sessions and long-running coding tasks from Telegram
- 🧵 **Telegram Forum Topics** with persistent Topic ↔ OpenCode session/directory bindings
- 🧠 **Model Center 3** as the single model-selection source of truth
- 🔎 Live model search, provider browsing, favorites, and recent models

- 🐙 GitHub integration for repository, issue, PR, and coding workflows

```text
                  ┌──────────────────┐
                  │ Telegram Bot     │
                  │ routing + UI     │
                  └────────┬─────────┘
                           │
             ┌─────────────┼──────────────┐
             ▼             ▼              ▼
       Main Chat       Forum Topics    Background
             │             │              │
             └─────────────┼──────────────┘
                           ▼
                 Topic / Session Router
                           │
                           ▼
                    OpenCode API
                    127.0.0.1:4096
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
     Model Center     Custom Providers   GitHub / MCP
          │                │                │
          └────────────────┼────────────────┘
                           ▼
                    Persistent `/data`
                           │
                  Railway Persistent Volume
```

### Topic architecture

Forum Topics are treated as first-class runtime contexts rather than as cosmetic Telegram threads.

- Each Topic can maintain its own OpenCode session/context.
- Topic bindings are persisted and restored across process restarts.
- Incoming messages and OpenCode event responses are routed through the active Topic context.
- Topic event subscriptions are scoped to the persisted binding to prevent cross-topic leakage.
- Topic deletion is failure-safe and idempotent; partial cleanup is reported accurately.
- Directory-only/ambiguous Topic routing is blocked instead of guessing the destination.
- Topic-specific settings are separated from Main settings.
- Reply-keyboard routing is normalized and emoji-safe.
- Explicit Telegram Topic context is preserved when sending event-driven responses.

This design is intended to make every Topic behave like a durable OpenCode workspace while keeping the main chat independent.

| Variable | Required | Description |
|---|:---:|---|
| `TELEGRAM_BOT_TOKEN` | ✅ | Token generated by @BotFather |
| `TELEGRAM_ALLOWED_USER_ID` | ✅ | Numeric Telegram user ID allowed to use the bot |

GitHub credentials, custom AI-provider keys, and other integrations are configured from Telegram and are **not** required as Railway environment variables.

### Runtime defaults

OpenCode runs locally inside the same container on `127.0.0.1:4096`. Normal Telegram polling does not require a public Railway domain or an exposed OpenCode port.

The persistent `/data` volume keeps provider credentials, memory, runtime state, session metadata, and other persistent data across restarts and redeployments.

## Telegram UI

The persistent bottom keyboard keeps common actions available without flooding the chat with navigation messages.

```text
┌──────────────────┬──────────────────┐
│ 🧠 Model         │ 💬 New Chat      │
├──────────────────┼──────────────────┤
│ 🕘 History       │ ⚙️ Settings      │
└──────────────────┴──────────────────┘
```

Advanced controls live inside **Settings**. Menus prefer editing the existing Telegram message, with **Back** for parent navigation and **Close** for Settings.

Topic-aware interfaces expose separate **Main** and **Topic** settings where behavior must be scoped to the current Telegram context.

## Model Center 3

**Model Center 3 is the canonical model-selection layer.** The old independent model-selector UI is not used.

- `⭐ Favorites` — persistent per-model favorites.
- `🕘 Recent models` — persistent recent-model history.
- `🔎 Search models` — search the live catalog.
- `🧩 Browse providers` — paginated provider/model browsing.
- Live custom-provider refresh when entering Model Center and periodically in the background.
- Custom-provider catalogs are treated as authoritative over stale local OpenCode copies.
- Runtime model callbacks use short-lived/bounded state instead of embedding large model identifiers in Telegram callback data.
- Selecting a model updates the persistent keyboard immediately and records the model in Recent Models.

## Custom AI Providers

Open **Settings → API Providers**.

The provider wizard collects:

1. Provider name
2. OpenAI-compatible Base URL
3. API key

The bot validates the provider, verifies the API key against the provider's API, discovers models from `/models`, stores credentials under `/data`, generates the OpenCode provider configuration, and publishes the verified live catalog to Model Center.

API keys are never rendered back to the user. Where Telegram permits it, the original message containing the key is deleted after processing.

Example:

```text
Provider: TabiToken
Base URL: https://tabitoken.com/v1
Model: claude-opus-4-8
```

See `docs/CUSTOM_PROVIDERS.md` for provider-specific details.

## AI: text, audio, and image workflows

The bot supports more than plain text coding sessions.

### Audio

- Speech-to-text can turn Telegram voice/audio messages into prompts.
- Optional text-to-speech can produce audio replies.
- STT/TTS configuration is kept separate from the core Telegram/OpenCode runtime.

### Image AI

Image-capable providers/models can be routed through the bot's AI configuration rather than being hard-coded into the text model selector. This allows image generation/vision-capable workflows to evolve independently from the coding model catalog.

The exact available image models depend on the configured providers and their live capabilities.

## Recent chat history

`🕘 History` exposes recent OpenCode sessions as compact inline buttons.

Selecting a session opens a bounded preview (up to the configured message limit, **10 by default**) and provides:

- `✅ Continue chat` — resume the selected OpenCode session.
- `← Back` — return to the session list.

History is intentionally a session-oriented UI; it does not blindly dump the full conversation into Telegram.

## GitHub integrations

GitHub is configured from **Settings → Integrations**.

Multiple GitHub credentials can be stored independently, and the active credential can be switched without changing Railway environment variables.

The active GitHub integration can be used for repository operations supported by the installed integration, including the development workflow used by the bot itself.

The bot exposes OpenCode capabilities that are useful from Telegram:

## Persistent memory

Memory is independent of the selected AI model.

```text
Claude → GPT → Gemini → Claude
              │
              ▼
       same persistent memory
```

Memory lives under `/data`. Only relevant, bounded memory is injected into prompts. It is separate from raw OpenCode session history, so changing models does not erase memory and the complete memory store is not sent with every request.

## Token Guard & usage telemetry

Token Guard is the central protection layer for context and request-cost control. It targets common causes of unexpectedly expensive requests:

- oversized context
- unnecessary tool context
- repeated retries
- runaway agent/tool turns
- excessive output/reasoning budgets

Request telemetry tracks input, output, reasoning, cache, and total usage so expensive requests can be diagnosed from measurements rather than guesses.

## Development & quality gates

Requirements: Node.js 22.14+, OpenCode, a Telegram bot token, and your Telegram user ID.

```bash
npm ci
npm run build
npm run typecheck
npm run lint
npm start
```

Before shipping changes, the intended validation loop is:

1. Review the relevant source and recent commit history.
2. Build and type-check the project.
3. Run focused tests/validation for the changed subsystem.
4. Deploy to Railway.
5. Inspect build/runtime logs for regressions.
6. Iterate on GitHub until the deployment is healthy.

## Security

- Keep `TELEGRAM_BOT_TOKEN` secret.
- Restrict access with `TELEGRAM_ALLOWED_USER_ID`.
- Custom provider API keys are stored under `/data` with restricted permissions and are never committed to Git.
- GitHub credentials configured through Integrations are stored separately from Railway environment variables.
- OpenCode is local to the container and should not be exposed publicly unless authentication and networking are intentionally configured.
- Avoid logging raw API keys, authorization headers, or other credential material.
