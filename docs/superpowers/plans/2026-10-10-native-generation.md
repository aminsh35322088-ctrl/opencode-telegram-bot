# Continuous Telegram native generation implementation plan

Goal: Give private AI Topics one continuous native draft and exact-run Stop throughout OpenCode execution and Telegram finalization.

Contract: https://core.telegram.org/bots/api#sendrichmessagedraft, #messagegenerationstopped and #inputrichblockexpandableblockquotation, inspected 2026-10-09. Private Topics are the production architecture. Drafts expire after 30 seconds, reuse chat/thread/draft identity, and require a separate persistent final message. Native Stop events contain no actor field. `keep_on_stop` is temporary retention, not persistence.

Architecture: TelegramRunPresentationController owns durable identity, bounded safe phase summaries, throttled native drafts and output fences. ControlPlane owns stop routing and delegates cancellation to the existing signed exact-run Worker RPC. Core remains process/resource authority. The response renderer and durable outbox remain final delivery authority. Legacy CloudRunUi is only the compatibility presentation for unsupported chats; no synthetic native Stop is added.

Constraints: Work on latest remote main; no workflows or PR; never export production credentials. Preserve ReplyKeyboard consume order, panel isolation/lifecycle, titles, numbering and renderer. Retain fallback controls until native Stop has real production evidence. No per-token presentation storage writes or Telegram updates.

1. Add failing lifecycle tests using real SQLite and Telegram transport mocks: stable scoped identity, all active phase transitions, safe summaries/no raw reasoning, transient tools, refresh/deduplication, retries, unsupported contracts, restarts, exact Stop, stale/replayed Stop and late events.
2. Implement a durable presentation table with a monotonically allocated draft ID and immutable owner fields. Keep in-flight status and phase changes bounded. Refresh at 10 seconds and coalesce at 1.5 seconds. Preserve can_stop on active updates including finalization; keep_on_stop false avoids garbage partials.
3. Add webhook regressions, subscribe to stopped_message_generation, admit native Stop using allowlisted private chat and exact draft binding, and fence synchronously before cancellation I/O. Reconcile CANCELLING after restart. Prevent queued runs from overtaking cancellation/finalization. Use existing Core stop/status operations.
4. Integrate presentation at admission, signed events, alarm updates and final delivery. Keep execution terminal outcomes distinct from presentation terminal state. Serialize final send admission; document that the Bot API has no atomic Stop-versus-send transaction. Respect ambiguous receipts and never duplicate final sends.
5. Gate ReplyKeyboard removal on native qualification per private chat. Consume old control labels without prompting the model. Preserve legacy unsupported-chat UI. Keep title/numbering/panel tests unchanged and run them with new tests.
6. Review full diff twice, including fresh independent reviewer. Run focused/full Node and Vitest suites, lint, typecheck, build, diff check and Wrangler dry-run. Push only exact tested changes directly to main. No Railway deployment if runtime code is unchanged.
7. Deploy preserving secret bindings. Exercise internal diagnostics via a temporary account-owned Worker bound to the production Durable Object, with short-lived authentication and no production secret export. Obtain live API acceptance, stable-ID updates, real Stop webhook/cancellation evidence and final delivery evidence. Remove diagnostic Worker. Verify exact Cloudflare version/tail/health and Railway status. Report any client-interaction evidence that cannot be obtained rather than claiming it.

Review focus: Stop during an in-flight draft; terminal callbacks during cancellation; ambiguous final sends; private Stop without from; Topic recreation; irreversible Telegram requests already accepted before Stop. Every operation rechecks durable ownership after awaits. Native availability cannot be guaranteed during Telegram outages/rate limits, so failures must be observable without losing execution ownership.
